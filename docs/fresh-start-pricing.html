At launch everything is cheap because there is almost no data. What decides the bill later is image traffic: at the viral stage the CDN is most of the cost on AWS, while Cloudflare R2 charges nothing for downloads. That is why the zoom-out scenario on the next page matters.

The scenario: a board with 2,000 images, zoomed fully out

Your biggest board today has 1,905 images (mostly screenshots, 127 KB on average). At 10% zoom, like your screenshot, every one of them is in view at once.

What the app does today

  • Yes, it fetches all of them. Images are set to load only when near the screen, but fully zoomed out all 1,905 are on screen, so the browser downloads every original: about 236 MB, to draw pictures 30 pixels wide.
  • The page also holds all 1,905 cards all the time (even when zoomed in), which is why very big boards pan more slowly.
  • Decoding 1,905 full-size screenshots takes a lot of memory; a phone may slow down or reload the tab.
  • After the first time the browser keeps them for a year, so it is fast again — until a new device or a cleared cache.

  1. Previews made at upload. The browser makes the 128, 256 and 1024 px WebP versions itself before uploading (measured on 120 of your screenshots: 1.7, 5 and 22 KB). No image library on the server, so it works on all six setups. Storage grows only ≈ 25%.
  2. Pick the version by zoom. Fully zoomed out: ≈ 3 MB instead of 236 MB, about 75× less traffic and memory.
  3. Draw only what is near the screen (and use simple blocks for text cards when zoomed far out), so big boards stay smooth.
  4. Load one board at a time. Today the app loads the whole account at sign-in; the hosted version should fetch only the open board (≈ 0.7 MB for 1,905 cards).
  5. Nearest first. Fetch images closest to the middle of the screen first, a few dozen at a time, and cancel those that leave the view.
Without previews, every first-time full zoom-out moves ≈ 236 MB: at the viral stage that alone would multiply the CDN bill on AWS many times over, and the Supabase plan's 250 GB would last about 1,000 zoom-outs.

The same zoom-out in each setup

Every setup below assumes the previews and per-board loading from the previous page. Each diagram shows the two things the browser fetches: ① the board's cards and ② its images.

0Plain Lightsail (everything on the server disk) the plan so far

What happens on a full zoom-out
  1. The board's 1,905 card rows come from SQLite in one request (milliseconds).
  2. The browser asks for 1,905 images. With HTTP/2 through Caddy it fetches many at once; the Node server checks each one belongs to you and streams it from disk.
  3. Everything comes from one machine in one place: friends far away wait longer, and a viral spike lands on this one server.
  4. The browser keeps each image for a year, so the second zoom-out costs nothing.

1Lightsail + S3 + CloudFront for files smallest step

What happens on a full zoom-out
  1. Card rows come from the Node server and SQLite, as above.
  2. At sign-in the server gives the browser a CloudFront signed cookie: one key that opens only that account's files, so 1,905 images need no 1,905 separate signatures.
  3. Images come from the CloudFront location nearest the user; only the first view goes back to S3. The server is not involved at all.
  4. A viral spike in image traffic hits CloudFront, not your server.

2ECS Fargate + RDS Postgres + S3 + CloudFront classic AWS

What happens on a full zoom-out
  1. The load balancer sends the request to any healthy container; it reads the board's rows from Postgres with one indexed query (user + board).
  2. Images: the same CloudFront path as option 1.
  3. If one container dies mid-zoom, the next request goes to another; RDS keeps a standby copy if you pay for Multi-AZ.
  4. More containers can be added automatically when many people zoom at once.

3Lambda + API Gateway + DynamoDB + S3 + CloudFront serverless

What happens on a full zoom-out
  1. One Lambda call runs a DynamoDB Query for that board. DynamoDB returns 1 MB per page, so ≈ 0.7 MB of cards is one or two pages.
  2. If nobody used the app for a while, the first call has a cold start of about half a second to a second.
  3. Images: the same CloudFront path as option 1 — no Lambda runs per image.
  4. Nothing runs (or costs) between requests.

4Cloudflare Workers + D1 + R2 edge

What happens on a full zoom-out
  1. A Worker in the city nearest the user reads the board's rows from D1 (the same SQL as today).
  2. Each image request also passes a Worker that checks the session, then is served from Cloudflare's cache or R2.
  3. R2 never charges for downloads, so a viral month costs requests, not traffic.
  4. Repeat views come from the browser cache or the nearest Cloudflare city.

5Supabase (Postgres + Storage + Auth) backend as a service

What happens on a full zoom-out
  1. The app asks Supabase for the board's cards directly; row-level security rules make sure only your rows come back.
  2. One createSignedUrls call signs all 1,905 image paths at once.
  3. Images come through Supabase's CDN; cached downloads are billed cheaper than uncached ones.
  4. Supabase can also resize images on request, but that is billed per image, so making previews at upload is cheaper.

Reading the numbers: one zoom-out costs a fraction of a cent everywhere once previews exist; the monthly price is mostly the fixed server cost at launch and image traffic at the viral stage. AWS has also added CloudFront flat-rate plans that may beat the per-GB prices above at the viral stage — worth checking. New AWS accounts get starting credits, and Lightsail often gives the first months free.
